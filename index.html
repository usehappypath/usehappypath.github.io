The problem

The bug nobody saw

It is Friday. You ship a small change to the pricing page. All tests pass. You go home.

On phones, the "Start free trial" button is now under the cookie banner. Nobody can tap it. Your tests do not use a phone. Your team does not look at the pricing page on a phone after every deploy.

On Monday, a customer writes: "Your trial button does not work." You lost three days of sign-ups.

The code was fine. The path was broken. Nobody walked it.

The idea

A careful visitor who never gets tired

Unit tests check your code. Uptime checks tell you the server answers. Neither tells you if a person can do what they came to do.

Happy Path does what a careful tester does by hand, every day, on every page:

  • It opens the site on a computer and on a phone.
  • It follows the main paths: from the home page to pricing, to sign-up, to search, to contact.
  • It reads the words. Do the numbers agree? Does the page keep its promise? Is anything old or confusing?
  • It only speaks when it is sure.

How it works

One day with Happy Path

  1. 1. Learn the site

    It finds your pages and the main things a visitor comes to do. For example: "compare plans", "start a trial", "find a guide". These are the paths. You can add or remove paths at any time.

  2. 2. Walk every path

    It walks each path step by step, on desktop and on phone. It takes a screenshot of every step. It clicks links, tabs and menus. It never submits forms, signs in or buys.

  3. 3. Check every page

    Broken links. Missing images. Script errors. Text cut off on a phone. Slow pages. Buttons under other things.

  4. 4. Read like a customer

    It reads the content. Prices that differ between two pages. A headline that promises something the page does not show. A date from last year. Words that a new visitor will not understand.

  5. 5. Prove it twice

    Every problem is replayed two times in a fresh browser. If it does not happen both times, it is not filed. A short outage or a slow network is not a bug.

  6. 6. Write it up

    One GitHub issue per problem, never duplicates. Each issue has the page, the steps, screenshots, what happens, what a visitor expects, and a suggested fix.

  7. 7. Check the fix

    When you say it is fixed, it tests the live site again. It closes the issue with proof, or reopens it with proof. If a fixed bug comes back later, it reopens the issue.

Start

Get started in three steps

  1. Install the app on the repo of your website. It gets one right: issues. It cannot read your code.
  2. Reply to the setup issue. The app opens an issue called "Set up Happy Path". Reply /happypath setup https://your-site.com.
  3. Prove the site is yours. Put a small file at /.well-known/happypath.txt that contains your repo name, like owner/repo. The first walk starts within the hour.

FAQ

Questions

Does it change anything on my site?

No. It only reads and clicks safe things like links, tabs and menus. It never submits forms, signs up, signs in, buys or sends messages.

Can it read my code?

No. The GitHub app has one right: read and write issues in the repos you choose.

Why do I need to put a file on my site?

So nobody can point Happy Path at a site they do not own.

How many issues will I get?

Only problems seen two times out of two. Medium severity and up by default. At most 10 new issues a day. One issue per problem.

What does it cost?

Nothing during early access. We test 10 sites at a time. When full, new sites join a waitlist, and the setup issue tells you your place.

Where are the screenshots kept?

In a public repo, usehappypath/evidence, so GitHub can show them in your issue. Only screenshots of public pages go there. To have yours removed, open an issue on this site's repo.

Does it test pages behind a login?

Not yet. Public pages only.

How do I stop it?

Uninstall the app in your GitHub settings. Testing stops at once. We delete your site's data within 30 days.
